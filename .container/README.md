# 検証コンテナ

この repo の zsh 設定を、実機を汚さずに検証するためのコンテナ環境。対話シェルに
入って手で触る使い方と、非対話でテストを走らせる使い方の両方を持つ。

ディレクトリ名がドットで始まるので、chezmoi はこの階層を無視する。実機には配置
されない。

## 使い方

```sh
.container/run build full        # イメージをビルド
.container/run sh full           # 対話シェルに入って手で触る
.container/run test full         # 非対話テストを走らせる (warm)
.container/run test full cold    # キャッシュを捨ててから走らせる
.container/run clean full        # プラグインキャッシュを捨てる
```

`full` の代わりに `minimal` を渡すと、`.zinit.zsh` が参照する外部ツールが無い
環境になる。`run` が受け取る環境変数は `run` の冒頭コメントにある。

## 2 つの variant

| variant   | 中身                             | 用途                                       |
| --------- | -------------------------------- | ------------------------------------------ |
| `minimal` | zsh, git, less, tar だけ         | `.zinit.zsh` の `has` ガードが効くかを見る |
| `full`    | + bat, eza, fd, fzf, vivid, walk | 関数・alias・キーバインドまで検証する      |

対話 / 非対話はイメージではなく起動引数で切り替える。同じイメージに `test`
を渡すとテストランナーが走る。

`run` は variant を `TEST_VARIANT` としてコンテナに渡し、テスト側はその宣言値を
期待値の根拠にする。実測したコマンドの有無で分岐させると、full からツールが
欠落しても「なし」側を正解として実行して green になってしまう。

イメージに入れていないもの。

- `zoxide` / `translate-shell` — `.zinit.zsh` が `from'gh-r'` / `sbin'...'` で
  自前取得する経路そのものを検証したいため
- クリップボード系の実物 — X/Wayland が無いと実行時に失敗し、ガードが効いた
  状態より紛らわしい。代わりに `stubs/ext/xclip` を使う
- `git-delta` — `git/config` は使うが zsh 設定からは参照されない
- `neovim` — `.profile` の契約は `EDITOR` の値であって、エディタの存在ではない
- 端末ごとの terminfo — 使う端末は変わるので焼き込まない。`run sh` が
  ホスト側の定義 (`infocmp -x $TERM`) を渡し、entrypoint が `tic` で取り込む。
  取り込めなければ `xterm-256color` に落とす

## cold と warm

`test` の第 3 引数はキャッシュの扱い。`warm` は既定で、プラグインキャッシュを
再利用する。`cold` はキャッシュを捨ててから走らせるので、新規マシンの初回起動と
同じ経路を通る。zinit の clone が走る分だけ遅い。

assertion の数は cold の方が 1 件多い。zinit が未インストールのときだけ、ランナーが
先に 1 回起動して「初回起動が終了コード 0 で終わる」を検証するため。数を run 間で
比べるときはモードを揃えること。

プラグインは revision を固定せず上流の HEAD を追うため、cold で失敗する変更が
warm では通り得る。どちらで走らせたかは結果のヘッダに出る。設定側の意図である
上流追従を変えたくないので revision は固定せず、代わりに解決された revision を
テスト出力に記録している。上流更新による差異はこの方針の帰結として残る。

## テストの前提

### 設定は層構造で、仕様は全層適用後の最終状態

「OMZ の基本設定 → `.zinit.zsh` の ice → `rc`」の順に読まれ、`rc` が最新かつ
最も変わりやすい層。テストは settle 後の最終状態だけを主張し、`.zinit.zsh` に
何が書いてあるかを根拠に期待値を立てない。

### chezmoi は使わない

chezmoi 命名から `$HOME` への対応表は `file-map.zsh` にある。repo 側で zsh 関連
ファイルを増やしたら追記が必要で、書き忘れは `pre-10` が検出する。

### `.zshrc` はコンテナ側で生成する

`.zshrc` は変更頻度が高いため repo の管理外で、実機では apply 後に手作業で
`. $ZDOTDIR/.zinit.zsh` を追記する運用になっている。`gen-zshrc.zsh` がその形を
再現する。実機の `.zshrc` そのものはここでは検証できない。

## 実行環境

### ホストの arch でネイティブに動かす

ベースイメージは `run` が選ぶ。

| ホスト | platform    | ベースイメージ                                      |
| ------ | ----------- | --------------------------------------------------- |
| x86_64 | linux/amd64 | 公式の `docker.io/library/archlinux:base`            |
| arm64  | linux/arm64 | 非公式リビルドの `docker.io/lopsided/archlinux`      |

amd64 をエミュレーションで動かすことはできない。qemu-user 下では Arch の zsh が
外部コマンドを fork した時点でハングする。組み込みコマンドだけなら動く。

```
zsh -c 'print OK'            # 通る
zsh -c '/bin/true; print OK' # 返ってこない
```

Alpine の musl 版 zsh は同じエミュレーションで動くので、glibc + qemu-user + zsh
の組み合わせ固有の問題。arm64 ホストで公式 archlinux イメージを使う道はここで
閉じている。

### ビルド中は pacman のサンドボックスを切る

pacman 7 のダウンロードサンドボックスは、環境によって seccomp の設定に失敗する。
`error restricting syscalls via seccomp: 22` で止まる。

### SELinux のラベリングを切る

`run` は `--security-opt label=disable` を付けて起動する。これを外すと、`run sh`
のたびに `gitstatus failed to initialize` が出る。p10k が `~/.cache` に取ってきた
gitstatusd を tar で展開する際にアーカイブ内の SELinux ラベルまで復元され、
podman が起動ごとに割り当てる MCS カテゴリと食い違うため、次のコンテナから読め
なくなる。同一コンテナ内では読めるので、1 回の run で完結するテストでは気付け
ない。詳細と `:z` が効かない理由は `run` のコメントにある。

repo を read-only で渡すだけの使い捨てコンテナなので、隔離を弱めるより実機と
同じ起動経路を再現できることを取っている。

## 作り直しが必要になる変更

### `entrypoint.zsh` と `stubs/` を直したら `run build`

設定とテストは mount した repo から読むが、この 2 つはイメージに焼かれている。
忘れると entrypoint が起動時に食い違いを検出して止まる。

### `Dockerfile` を直したら `cold`

named volume はイメージを焼き直しても残る。パッケージ構成が変わると、古い
キャッシュに残った壊れたインストールが `warm` では直らない。`tar` を足したあと、
tarball だけ落ちて展開されていない zoxide が残り続けたことがある。

`Dockerfile` とビルド引数から計算した指紋をイメージと volume の両方に持たせ、
食い違ったら entrypoint が止める。自動では捨てない。指紋は `Dockerfile` 全体の
ハッシュなので、コメントだけを直しても cold が必要になる。

指紋の入力に `entrypoint.zsh` と `stubs/` は含めない。あれらはハーネスの
振る舞いであってプラグインの入り方には影響せず、含めると触るたびにキャッシュが
飛ぶ。

## テストの構造

`tests/` 配下は 4 群。群ごとにセッションの前提が違うので、同じ前提のテストが
1 セッションを共有する。

| 群       | セッション                                | 見るもの                                                   |
| -------- | ----------------------------------------- | ---------------------------------------------------------- |
| `pre-*`  | 疑似端末なし                              | 同期ロード経路、起動時の stderr、イメージの中身、配置、対話パスのロジック |
| `pty-*`  | `zpty` の対話ログインシェル、`TERM=linux` | 関数・alias・キーバインド・実キー操作                      |
| `p10k-*` | `TERM != linux` の別セッション            | p10k のロードとプロンプトの内容                            |
| `ext-*`  | PATH に `stubs/ext`、`DISPLAY` 設定       | 外部コマンドをスタブに差し替えた枝                         |

スタブを別セッションに分ける基準は「他のテストの前提を壊すか」。今ある `xclip`
のスタブは他の枝に影響しないので、`ext-*` の 1 セッションで足りる。`uname` の
ようにロードされる枝そのものを変えるスタブを足すなら、群を分ける必要がある。

新しい群を足すなら `runner.zsh` の群ごとの非空検査にも追加する。

### 端末関連の環境変数

`test` は `TERM` を固定する。`pty-*` と `ext-*` は `linux`、`p10k-*` は
`xterm-256color`。ホストの端末で結果が変わると再現しないため。同じ理由で
`COLORTERM` も渡さない。

`run sh` は逆に、ホストの `TERM` と `COLORTERM` をそのまま渡す。実際の利用環境を
再現したいため。truecolor は terminfo の `Tc` / `setrgbf` だけでなく `$COLORTERM`
でも判定され、p10k と bat はこちらを見るので、両方要る。

### タイムアウト

`zpty -r` にタイムアウトが無いので、待ち時間の上限は内側と外側の二重で持つ。

| 変数                | 既定  | 対象                                     |
| ------------------- | ----- | ---------------------------------------- |
| `TEST_TIMEOUT`      | 2400s | ランナー全体。entrypoint が `timeout` で被せる |
| `PTY_START_TIMEOUT` | 600s  | 各 pty セッションの初回応答。zinit の clone を含む |
| `PTY_READ_TIMEOUT`  | 120s  | 2 回目以降の読み取り                     |

外側は内側の合計より大きく取る。pty セッションは 3 つあるので、初回応答だけで
最大 1800 秒を使う。`TEST_TIMEOUT` をその合計と同じにすると、内側が上限に達して
どのテストで詰まったのかを報告する前に、外側が全体を殺してしまう。

`run` はこれらをコンテナに渡さない。変えるなら `run` に受け渡しを足す。

### テストを足すとき

ハーネスの仕組みと落とし穴はコード側のコメントに書いてある。`zsh -i -c` を使わ
ない理由、ロード完了の待ち方、ブラケットペーストと実キー送出の使い分けは
`tests/lib.zsh` にある。読まずに書くと必ず踏むので、各ヘルパのコメントを先に
読むこと。

## 検証で分かったこと

- **`tar` の不在:** 無いと zinit の展開が静かに全滅する。`tar` は Arch の `base`
  に含まれ実機には必ずあるが、arm64 のリビルドイメージには無かった。起動時に
  `zinit-extract: command not found: tar` が出るだけで、gh-r のバイナリも p10k の
  gitstatusd も展開されない。個別の assertion は素通りする。
- **arm64 の `zoxide`:** x86_64 バイナリのまま展開される。ice が
  `bpick '*x86_64-unknown-linux*'` で固定されているため。ホストに x86_64 の
  binfmt が登録されていれば qemu 経由で動いてしまうが、それは環境依存の偶然なので
  当てにしないこと。
- **`trans.e2j` のエイリアス:** 関数本体にエイリアスの解決結果が焼き込まれる。
  translate-shell プラグインは `trans` をエイリアスとして張り、zsh のエイリアス
  展開はパース時に起きる。`trans.e2j` を定義する `atload` がパースされる時点で
  エイリアスがあると、関数本体に実物のパスが埋め込まれる。turbo のロード順に
  よってどちらになるかが変わるので、実行ごとに結果が違う。
- **`clipcopy` の非同期性:** OMZL::clipboard.zsh の xclip 分岐は
  `... | xclip -selection clipboard -in &>/dev/null &|` と書き込みを disown した
  非同期ジョブで走らせる。スクリプトで `clipcopy` の直後に `clippaste` すると
  競合する。

## 既知の制約

この範囲で green になっても「zsh 設定全体が検証できた」ことにはならない。

- **実キー送出の範囲:** autopair、surround、history-substring-search、dirstax の
  4 つ。fzf の widget (`^T` / `^R`)、`fzf-tab` の補完、`walk-lk-widget` は実行が
  対話的なので、登録の確認までしか見ていない。PATH にスタブを置いたセッションを
  足せば届く。
- **p10k:** プロンプトの内容までしか見ていない。git のブランチ名が出ることは
  確認しているが、Nerd Font のグリフと instant prompt の 2 段出力は検証していない。
- **対話パスの通し検証:** `.zshrc` の生成と TERM の解決は `pre-20` が直接呼んで
  検証しているが、「生成した `.zshrc` を読ませた状態で ⌘ + 矢印が張られるか」と
  いう通しの確認は入っていない。
- **`run sh` の色の見え方:** terminfo の取り込みは `pre-20` が見ているが、
  `TERM` と `COLORTERM` の受け渡しは検証していない。
- **Darwin 分岐のテスト:** dirstax は `uname -s` で macOS 用のキーバインドに分かれ、
  `.zinit.zsh` は zoxide のロードを同じ条件で切り替えるが、実機の Arch も x86_64 の
  コンテナも Linux なのでその枝は実行されない。この dotfiles の対象環境ではないため、意図的に検証していない。
  検証するなら `uname` のスタブを載せた群を足せば届く。
- **chezmoi との照合:** 実物の `chezmoi apply` と突き合わせれば配置の検証は完全に
  なるが、「chezmoi を持ち込まない」前提を崩す。代わりに `pre-10` が期待値を直書き
  して突き合わせている。
- **xclip と X サーバ:** 実物を使っていない。スタブは経路を通すだけで、X への接続や
  selection の区別は検証していない。
- **`e2j` / `j2e`:** 翻訳コマンドを差し替えられないため検証していない。`e2j` は
  「入力を取る」「整形する」「翻訳する」を 1 本のパイプラインに固定しており、末尾の
  `trans.e2j` には上記のとおりエイリアスの解決結果が焼き込まれる。PATH にスタブを
  置いても届かない。テストのために設定側の構造を変えるのは本末転倒なので、検証しない
  ことにした。整形ロジックである改行の連結とハイフネーション除去も、公開コマンド経由
  では観測できないため対象外。
- **イメージのタグ:** `minimal` / `full` のタグ名を arch 間で共有する。ホストを
  変えて使う場合はビルドし直すこと。また `--target full` のビルドは `minimal` タグを
  更新しないので、両方使うなら両方ビルドすること。
